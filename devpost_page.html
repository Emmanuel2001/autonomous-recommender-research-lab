What it does

One iteration, five steps

  1. Proposes six competing hypotheses, one per research lane — architecture, objective, sampling/training, features, optimisation/regularisation, ensembling.
  2. A judge ranks them and funds exactly one, and must give a verdict on every candidate by id, not just the winner.
  3. The agent writes the code, editing any of config.json, features.py, model.py, train.py in a mutable workspace.
  4. The hypothesis, the resulting tree hash and the harness-computed diff are pre-registered in a signed ledger before the candidate is allowed to run.
  5. It fits, scores, and reflects — updating a structured belief keyed by mechanism, recording whether that mechanism was supported or contradicted and under what condition it may be retried.

The champion is immutable and advances only on a signed validation improvement, so a bad run can spend budget but cannot damage the submission.

What failed

The section worth reading first

The failures are better evidence that the loop is real than the +0.0019 is.

The agent's own BPR implementation was broken — and the harness caught it

On the pointwise-only minimal profile the agent wrote step_bpr plus per-user negative sampling across model.py and train.py: a genuine multi-file implementation. It scored −0.206874, far below the 0.5 random floor, with train (0.3156) worse than validation (0.3948).

The defect: the optimiser expects dLoss/dz and descends, but the BPR step passed +σ(−diff) to positives and −σ(−diff) to negatives — both signs inverted. It performed gradient ascent, training the model to rank negatives above positives.

One iteration was silently inert

The agent implemented feature-level dropout properly — constructor parameter, inverted-scaling binomial mask, training=True correctly threaded into the training path — but never passed the config value into the constructor, so the default 0.0 stood and "dropout": 0.1 was dead code. The result was bit-identical to its parent to 15 significant figures, and deduplication could not see it because the tree hash genuinely differed. 38,113 tokens re-derived the champion.

Architecture: considered nine times, promoted zero times

Lane coverage is required by the tournament validator, so a model_architecture candidate appearing is the policy working, not the agent showing initiative. The report states this in its own words rather than letting a “considered” column imply curiosity.

Two more, recorded rather than smoothed over. The reflector diagnosed the BPR failure as “improper gradient alignment or sampling mismatch” at confidence 0.95 — directionally near, but it never identified the sign inversion. And the agent over-predicted its own gain on essentially every scored iteration; predicted and actual are printed side by side rather than hidden.

One distinction I want to be exact about

The compliant run above ran on the inherited profile, where a working pairwise implementation already existed and the ledger records pairwise_code_present: true. At iteration 1 the agent observed that implementation and changed only config.json, a 202-byte diff. So that run is an independent tournament-driven search route to essentially the same performance — it is not an independent authorship of the objective. The only genuine from-scratch BPR implementation is the one that failed.

What I learned

Mostly about measurement

  • A test that cannot fail is worse than no test. Of 38 defects found in one review sweep, 12 were in tests and 5 could not fail — including the two guarding the invariants I would have defended most confidently. What found them: after fixing a defect, sweep for its class across every module instead of re-reading the file it appeared in.
  • A measurement that confirms what you expect should be verified before it is acted on. Nine times the measurement was wrong rather than the code — a filter that could not display the outcome I was not expecting; a timeout binary that does not exist on macOS, which made 28 passing suites report as failures; a single successful API probe read as “the quota reset”.
  • Never let a test-set number justify a protocol decision. I once used a test-derived delta to argue about the convergence threshold. The correct figures were validation-only, and smaller. The episode is recorded in the repository rather than quietly deleted.
  • A wall-clock field that reads 0.0 will be believed. Per-iteration records were written inside the timing context, where the duration had not yet been assigned, so every iteration logged wall_seconds: 0.0 against stage sums of 11–18 seconds. The fix ships with a mutation-tested invariant — every record's wall time must be at least its own stage sum — confirmed to fail when the fix is reverted.

Limitations

Stated plainly

  • Only the cheapest model tier (gemini-3.5-flash-lite) has ever driven this loop. Whether a stronger tier reaches for architecture is untested.
  • No model_architecture candidate has been selected and successfully promoted.
  • The secondary effects around the pairwise objective are small or unresolved, not disproved: the negative-sampling change lost on a single search iteration rather than a 20-seed ablation, user_hist_len helped in the original lineage, and the L2-plus-cosine step was never confirmed against its immediate parent across seeds.
  • The train/dev gap is a diagnostic: the harness verifies the size of the returned train-subset vector but cannot verify which rows produced it.
  • Docker isolation is implemented but unexercised; the measured boundary is the macOS seatbelt sandbox.

What's next

In priority order

  1. A divergence guard. A monotonically rising training loss is an unambiguous abort signal from epoch two, and would have handed the coder a far sharper repair signal than “primary was 0.39”.
  2. An inert-change detector. A delta of exactly zero with an identical train metric means semantically inert — cheap to flag, and it recovers an evaluation slot that hash-based deduplication structurally cannot see.
  3. Component ablations over 20 seeds, to turn the unresolved secondary effects into measurements.
  4. A stronger tier on the architecture lane, the one open question the budget never let me answer.

How to verify

Nothing here is asserted on trust

python3 -m core.scorer verify --ledger runs/ledgers/research_submission.jsonl
python3 -m agent.research_report --ledger runs/ledgers/research_submission.jsonl
for f in tests/test_*.py; do python3 "$f"; done

The signed chain re-verifies; artifact hashes and pre-registration ordering are recomputed by the report itself. submission_compliant/MANIFEST.json binds the submitted predictions to the champion tree hash, the signing sequence number, and the score vector's own SHA-256. Diagnostic and compliant runs live in separate ledgers, because a run with the stopping rule switched off is not evidence about the official protocol.
